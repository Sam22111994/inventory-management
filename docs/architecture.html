Factory Inventory Management System

Architecture overview of a full-stack demo application: a Vue 3 single-page dashboard backed by a FastAPI service serving in-memory mock data. There is no database.

System architecture

Three tiers, two processes, communicating over REST/JSON.

Frontend Vue 3 + Vite · :3000

Router (6 routes) Views: Dashboard, Inventory, Orders, Demand, Spending, Reports Components: FilterBar, detail modals, TasksModal, ProfileMenu, LanguageSwitcher Composables: useFilters, useAuth, useI18n api.js (axios client)
▼ HTTP / JSON · http://localhost:8001/api · CORS open to all origins ▼

Backend FastAPI + Uvicorn · :8001

Route handlers (main.py) Pydantic models (validation / response schemas) Filter helpers: apply_filters, filter_by_month Aggregations: dashboard summary, quarterly reports, monthly trends
▼ Loaded once at startup via mock_data.py ▼

Data In-memory · JSON files

inventory.json orders.json demand_forecasts.json backlog_items.json spending.json transactions.json purchase_orders.json

Data flow

How a filter change on screen becomes updated data.

  1. User changes a filterFilterBar updates shared singleton refs in useFilters: period, warehouse, category, order status.
  2. View builds the requestgetCurrentFilters() maps state to query params (period becomes month). api.js drops any value equal to all.
  3. Axios calls the APIFor example GET /api/orders?warehouse=...&status=...&month=....
  4. FastAPI filters in memoryHandlers run apply_filters and filter_by_month over the lists loaded from JSON; the dashboard endpoint also computes totals.
  5. Pydantic validates the responseresponse_model enforces the schema before JSON is returned.
  6. View rendersRaw results are stored in refs (allOrders, inventoryItems); charts, tables and KPIs are computed properties derived from them.

Key design patterns

Frontend

  • Shared filter state is a module-level singleton, so all views see the same filters.
  • Raw data lives in refs; derived data lives in computed properties.
  • All HTTP access is centralised in api.js.
  • Language switching (en/ja) via useI18n and locales/.

Backend

  • JSON loaded once at import time; changes do not persist across restarts.
  • Shared filter helpers keep query semantics consistent across endpoints.
  • Pydantic models define response contracts.
  • generate_data.py regenerates the sample datasets.

Observations

Gap between client and server. client/src/api.js calls /api/tasks (GET, POST, PATCH, DELETE) and /api/purchase-orders (POST, GET). A search of server/main.py found no matching routes, although purchase_orders.json is loaded and read by the backlog endpoint. Those calls would return 404 against the current backend. This is worth confirming before relying on the tasks or purchase-order features.

Other current-state notes: no authentication, CORS allows all origins, and the API base URL is hard-coded to localhost:8001. Suitable for local demo use only.
